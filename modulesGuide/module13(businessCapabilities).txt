Theek hai bhai, pehle research karta hun, phir guide dunga.Research ho gayi. Guide ke andar jo cheezein daali hain, unka nichod:

- Gartner ne May 2026 mein Process Mining Magic Quadrant ko Process Intelligence Platforms MQ se replace kiya. Ab scope process mining, task mining, modeling aur monitoring, chaaron ka hai. Isliye M1 mein modeling aur mining ek hi jagah hain, aur BPMN ISO 19510 standard hai.
- PPM mein projects ROI, risk, urgency aur strategic fit ke weighted scoring se chune jate hain. Governance boards ko scoring model calibrate karne ke liye completed projects ka actual benefit bhi dekhna chahiye. Isliye M2 mein score vs actual-benefit calibration hai.
- Quality mein containment root cause analysis se pehle hota hai, "human error" kabhi root cause nahi hota, aur sirf retraining sabse kamzor corrective action hai. Yeh rules M3 ke NCR/CAPA engine mein validations ban gaye hain.
- Change mein Prosci ka change portfolio change saturation aur collision ko ek saath dikhata hai. Aur communication plan se pehle impact assessment chalta hai. M4 isi order mein bana hai.
- KM ke liye ISO 30401 ek management-system standard hai, aur sirf technology kharidna kaafi nahi. Ek research paper ke hisaab se knowledge graph wala RAG complex documents (base contract + amendments) par plain vector RAG se behtar chala.
- Content mein AI-generated assets ke liye provenance ab zaroori ho raha hai: C2PA manifest batata hai kis tool aur organization ne, kab content banaya. EU AI Act ki transparency dates sources mein alag-alag dikhi, isliye rules config mein hain.
- Benchmarking mein internal, external, performance aur practice, chaar type hote hain. Aur APQC ke mutabiq dashboard mein 5 se 15 KPIs aur unke neeche supporting measures rakhne chahiye.
- Analytics ka lifecycle CRISP-DM jaisa iterative hota hai (modeling data issues dikhaye to preparation par wapas). Lekin CRISP-DM risk aur ethics steps cover nahi karta, isliye M8 mein model-risk governance alag se hai.
- EHS mein permit-to-work, LOTO, SIMOPS aur Management of Change ek connected flow hain. TRIR, LTIFR aur severity rate incident data se auto-calc hote hain.
- Sustainability mein rules 2026 mein kaafi badle. Omnibus I ke baad CSRD scope 1,000+ employees aur €450M+ turnover tak simit hai, aur revised ESRS 3 July 2026 ko adopt hue (FY2027 se lagu). India mein BRSR top 1,000 listed companies ke liye hai. Ek hi data layer ESRS, ISSB aur BRSR Core, teeno ko feed kar sakti hai.

### Core Logic
1. Har published process ka exactly ek active owner hona chahiye. Owner exit/role change par HR event se reassignment task auto-create.
2. Publish flow governance cycle se: review → endorsement → approval → publish. Publish ke baad version immutable, edit par naya version, aur purane version `effective_to`.
3. Process hierarchy (L1-L5) mein child ka owner parent ke steward group se allowed. Cross-functional process ke kam se kam do function owners.
4. Mining ke liye event log import hota hai, aur conformance = designed model vs actual traces. Variants aur bottlenecks `bc_conformance_results` mein.
5. Control point har high-risk step par mandatory (risk rating se). Bina control wala high-risk step publish par warning.
6. Control test due dates se pehle owner ko reminder. Test fail hone par `capa_actions` auto-create.
7. Published BPMN workflow engine config mein compile ho sakta hai, lekin sirf approved version se aur governance sign-off ke baad.
8. Additional metric tabhi active jab data source aur owner defined ho aur measure Module 7 ke catalog mein register ho jaye.
9. Support-request themes (repeat questions) se SOP/training update task auto-suggest hota hai.
10. Improvement methodology rule-based suggest hoti hai (variation problem to DMAIC, flow problem to Lean, rule-based repetitive to RPA). Final choice owner ki.
11. Improvement project close hone par benefit validation 30/60/90 din baad (`benefit_register`), aur control plan active.
12. AI draft sirf draft status mein banta hai, human verify ke bina review step mein nahi jata.
13. Har change `audit_log` mein.

### Core Logic
1. Koi project portfolio mein tabhi aata hai jab demand request scored aur approved ho, aur approved business case ho. Strategic alignment mandatory, sirf financial ROI par approval nahi.
2. Score = weighted sum of criteria (`bc_scoring_criteria`). Weights config mein. Score ke saath capacity check chalta hai, aur capacity na ho to "approved but unscheduled".
3. Capacity what-if scenarios Deliver Services ke resource capacity se chalte hain. Resource conflict dikhane par project shift/stop ke options.
4. Gate review decision `continue / hold / rescope / stop`. Stop par resources release aur committed budget freeze.
5. Business case NPV/IRR/payback config discount rate se. Benefits ka owner mandatory, aur har benefit `benefit_register` mein.
6. Scoring-model calibration: closed projects ka predicted vs actual benefit compare hota hai, aur governance board ko calibration report jati hai.
7. Methodology advisor rule-based hai. Recommended se alag method choose ho to reason + approval.
8. EVM: SPI = EV/PV, CPI = EV/AC, EAC = BAC/CPI (default), method config. Threshold cross par auto-RAG red aur escalation.
9. Re-baseline sirf reason + approval ke saath. Purani baseline history mein rehti hai, aur variance original aur latest dono se dikhta hai.

### Core Logic
1. Aspect/hazard significance score config matrix se. High/significant items par controls + objective + owner mandatory, aur review date.
2. Hazard control hierarchy enforce: ppe/admin controls akele high-risk par accept nahi hote, elimination/substitution/engineering considered hona chahiye (reason logged).
3. Event create hote hi severity se workflow: major par investigation team auto-form, reportability engine statutory deadline timer (`obligations_register` + jurisdiction config) start karta hai.
4. Investigation root cause mein "human error" akela accept nahi (Quality ka same validation). Actions `capa_actions` mein.
5. CAPA close hone ke liye evidence upload mandatory, effectiveness check scheduled.
6. TRIR = recordable cases x 200,000 / hours worked (base config, jaise 1,000,000 bhi allowed). LTIFR = lost-time injuries x 1,000,000 / hours worked. Hours worked HR/T&A se.
7. Permit-to-work: request, hazards + controls, approval, activation, monitoring, closure. SIMOPS conflict check same area/time ke permits par. Permit expiry par auto-suspend aur alert.
8. LOTO record PTW se linked. Release se pehle sab locks off hone chahiye.
9. MOC request ke bina safety-critical process/equipment/org change implement nahi (Change module + Deliver Services change se link). MOC close hone tak related PSSR/training pending.
10. Training matrix: role x hazard ke hisaab se required course. Training gap wale employee ko high-risk permit/task par assign block (Deliver Services allocation/permit check).
11. Legal register change par affected sites ko compliance re-evaluation task. Permit/licence expiry se 90/60/30 din pehle reminder.
12. Emergency drill due date aur result findings `capa_actions` mein. Mass notification acknowledgement aur muster live count.
13. Medical surveillance data strictly confidential, sirf occupational health role ko, aur reports mein sirf aggregate.
14. EHS KPIs aur emissions/waste data Module 10 (sustainability) ko feed karte hain.
15. Har event, permit, closure `audit_log` mein.

### Core Logic
1. Applicability entity-wise evaluate hoti hai: thresholds (employees, turnover, listing, non-EU group turnover), jurisdiction aur reporting wave `bc_sus_applicability` + config se. Rules badle (jaise Omnibus I, revised ESRS) to config update, code nahi. Coverage ke figures sources mein thode alag dikhe (jaise BRSR Core assurance ki range), isliye final applicability SEBI/EU ke official text se verify karke config mein daalo.
2. Double materiality: impact score aur financial score dono thresholds se material topics nikalte hain. Sirf material topics ke datapoints mandatory, baaki "not material" reason ke saath.
3. Ek metric kai frameworks ke datapoints se map ho sakta hai. Ek baar data collect, multi-framework output (ESRS/ISSB/BRSR/GRI).
4. Activity data sources: utility bills, ERP/procurement spend, HR (headcount, diversity, training hours), EHS (injury rates, waste, emissions), Deliver Services facilities (energy). Maker-checker approval, evidence attach.
5. Emission = activity quantity x factor. Factor versioned aur valid-date se. Scope 2 location-based aur market-based dono. Scope 3 category-wise (supplier-specific ya spend/average-data method, uncertainty tag ke saath).
6. Target progress = base year vs actual vs pathway. Pathway se peeche chale to RAG red aur initiative suggestions.
7. Statement ka har number `source_calc_ref` se trace hota hai: number to calculation to activity data to evidence. Trace missing ho to statement approve nahi.
8. Assurance workpaper level (limited/reasonable) applicability se. Assurance-ready datapoints ka evidence lock hota hai, aur baad mein change par restatement log mandatory.
9. Filing se pehle approvals: sustainability head, CFO/legal, audit committee (config). Approved report immutable.
10. Digital tagging (XBRL/iXBRL) mapping taxonomy version ke saath, jahan regulator chahe. Validation fail par filing block.
11. Supplier ESG scores Scope 3 aur procurement risk dono ko feed karte hain.
12. Sustainability measures Module 7 ke measure catalog mein, targets Module 2 (initiatives) aur Module 4 (change) ke saath linked.
13. Har number, approval, restatement `audit_log` mein.

# CROSS-MODULE CONNECTIONS (kaun kise feed karta hai)

- **M7 (measures)** poore tool ka metric source hai: M1 process KPIs, M2 portfolio/benefits, M3 quality KPIs, M4 adoption, M5/M6 KM-content measures, M9 EHS KPIs, M10 sustainability metrics, aur Deliver Services ke KPIs sab yahin certified hote hain.
- **M7 gap → routing:** "need for change" PPM demand (M2), process improvement (M1) ya change initiative (M4) ban jata hai.
- **M1 ↔ Deliver Services:** published process/SOP wahi hai jo delivery staff dekhta hai, aur workflow engine mein compile hota hai.
- **M2 ↔ Deliver Services:** project resource requests Module 4 (resource planning) ko jati hain, aur capacity PPM scenarios ko feed hoti hai.
- **M3 + M9 + audits:** ek hi `capa_actions` engine. Quality NCR, EHS incident aur audit finding sab ka CAPA ek jagah.
- **M5 + M6:** KM assistant sirf M6 ke approved, fresh, classified content se jawab deta hai.
- **M9 → M10:** EHS ka waste/emissions/injury data sustainability statements mein jata hai. HR (diversity, training) aur Deliver Services facilities (energy) bhi.

**Suggested build order:** pehle Common Foundation, Module 7 (measure catalog), Module 1 aur Module 2 (ye baaki sab ke base hain). Phir Module 3 + 9 (CAPA engine), phir Module 4, 5, 6. Last mein Module 8 (analytics) aur Module 10 (sustainability, kyunki ye baaki sab ka data consume karta hai).

Do baatein yaad rakhna. Tab/ID counts is APQC tree ke hisaab se hain, agar tera PCF version alag ho to labels ek baar match kar lena. Aur Module 10 ke regulatory rules (CSRD thresholds, BRSR Core coverage, AI-content labelling dates) 2026 mein badal rahe hain, isliye unhe hamesha config table mein rakhna aur launch se pehle official text se verify karna.
